# 代码复用思维指南

> **目的**：写新代码前先停下来想——它是不是已经存在？
>
> 重复代码是不一致性 bug 的头号来源：修 bug 无法传播、行为随时间分叉、代码库越来越难懂。

---

## 写新代码之前

### 第一步：先搜

```bash
rg "functionName" core/ statusbar/ zusage.py
rg "常量或值" core/ statusbar/
```

### 第二步：过一遍问题表

| 问题 | 如果是…… |
|---|---|
| 已有相似函数？ | 用它或扩展它 |
| 这个模式在别处出现过？ | 照现有模式做 |
| 能否成为共享工具？ | 放到正确的单点位置 |
| 我在复制另一个文件的代码？ | **停**——提取到共享处 |

## 本仓库的真实教训

### 教训 1：双侧白名单镜像（最重要的复用单点）

`core/runtime_lock.py` 的 `RUNTIME_FILE_NAMES` ≡ `core/release_unpack.py` 的 `CORE_FILES`（23 项文件清单）。解包器刻意不 import（必须自洽），但清单改一边漏一边的结果是**一边拒装、一边缺文件**。

防回归手段：`tests/core_runtime_sync_basic.py` 专门断言两侧镜像一致。**当两个机制必须产出同一文件集时，要么消除不对称，要么必须有一致性回归测试**。

### 教训 2：清单常量单点复用

`core/sync_plugin.py:29` 的复制清单直接复用 `runtime_lock.RUNTIME_FILE_NAMES`，而不是自己维护一份——三个消费者（锁、解包器、同步器）共享一个真值来源。新增「要分发哪些文件」类需求时，永远回到 `runtime_lock.py` 单点，不要新建清单。

### 教训 3：同款助手跨文件复用

`L(zh, en)` 双语输出在 `core/install.py:156`、`core/patch_install.py:112`、`zusage.py:122` 是同款约定；`file_lock` 在锁与渲染桥链共用同一把 `app.asar.zcstatusbar.lock`。需要新助手时先搜 `rg "def L(" core/`——大概率已有实现，照签名复用。

### 教训 4：改名必须清理残留

`ZUSAGE_*` 旧命名空间已迁移为 `ZCODE_STATUSBAR_*`，运行时**零使用**，仅存在于各文件头的改名对照注释（如 `core/patch_install.py:12`）。教训：改名时同批清理所有引用与兼容别名（`ZUSAGE_LINE_RE = STATUSBAR_LINE_RE` 这类别名要注释保留原因），不要留下「看似在用」的死名。

### 教训 5：状态判定用穷尽分支

Python 的 if/elif 链没有穷尽性检查。本仓库的对策是**严格相等 + 显式默认**：聚合只认 `status === 'completed'`（`statusbar/session-stats.cjs:114`），行 kind 缺省显式按 `'model'`（CONTRACT §4.3）。给状态类字段加新值时，搜索所有切换该字段的分支并逐一补齐，不依赖 else 兜底正确。

## 何时抽象

**抽**：同代码出现 3+ 次、逻辑复杂到可能有 bug、多个文件都依赖同一真值。

**不抽**：只用一次、平凡单行、抽象比重复更复杂。本仓库刻意保留的不对称：解包器不 import 白名单（自洽优先），用测试兜一致性。

## 批量修改之后

1. **复查**：改全了吗？
2. **搜索**：`rg` 找漏网实例。
3. **考虑**：该提取单点吗？该加镜像断言测试吗？

## 提交前检查表

- [ ] 搜过相似代码，没有应共享而未共享的复制
- [ ] 清单/常量回到单点（runtime_lock.py / CONTRACT.md / usage_stats.py）
- [ ] 改名已清理所有残留与兼容别名
- [ ] 同类模式用同一结构（工厂注入、`L()`、原子写五连）
